<h2>3.3 挖掘SimpleSection.o</h2>

<p>前面對於目的檔只是作了概念上的闡述，如果不徹底深入目的檔的具體細節，相信這樣的分析也只是泛泛而談，沒有真正深入理解的效果。就像知道TCP/IP協議是基於包的結構，但是從來卻沒有看到過包的結構是怎樣的，包的頭部有哪些內容？目標地址和源地址是怎麼存放的？如果不瞭解這些，那麼對於TCP/IP的瞭解是粗略的，不夠細致的。很多問題其實在表面上看似很簡單，其實深入內部會發現很多鮮為人知的秘密，或者發現以前自己認為理所當然的東西居然是錯誤的，或者是有偏差的。對於系統軟體也是如此，不瞭解ELF檔案的結構細節就像學習了TCP/IP網路沒有了解IP包頭的結構一樣。本節後面的內容就是以ELF目的檔格式作為例子，徹底深入剖析目的檔，爭取不放過任何一個位元組。</p>

<p>真正了不起的程式設計師對自己的程式的每一個位元組都瞭如指掌。</p>

<p>我們就以前面提到過的SimpleSection.c編譯出來的目的檔作為分析物件，這個程式是經過精心挑選的，具有一定的代表性而又不至於過於繁瑣和複雜。在接下來所進行的一係列編譯、連結和相關的實驗過程中，我們將會用到第1章所提到過的工具套件，比如GCC編譯器、binutils等工具，如果你忘了這些工具怎麼使用，那麼在閱讀過程中可以再回去參考本書第1部分的內容。圖3-1中的程式程式碼如清單3-1所示。</p>

<p>3.3.2 資料段和只讀資料段</p>

<p>.data段儲存的是那些已經初始化了的全域性靜態變數和區域性靜態變數。前面的SimpleSection.c程式碼裡面一共有兩個這樣的變數，分別是<code>global_init_varabal</code>與<code>static_var</code>。這兩個變數每個4個位元組，一共剛好8個位元組，所以“.data”這個段的大小為8個位元組。</p>

<p>SimpleSection.c裡面我們在呼叫“printf”的時候，用到了一個字串常量“%d\n”，它是一種只讀資料，所以它被放到了“.rodata”段，我們可以從輸出結果看到“.rodata”這個段的4個位元組剛好是這個字串常量的ASCII位元組序，最後以\0結尾。</p>

<p>“.rodata”段存放的是只讀資料，一般是程式裡面的只讀變數（如const修飾的變數）和字串常量。單獨設立“.rodata”段有很多好處，不光是在語義上支援了C++的const關鍵字，而且作業系統在載入的時候可以將“.rodata”段的屬性對映成只讀，這樣對於這個段的任何修改操作都會作為非法操作處理，保證了程式的安全性。另外在某些嵌入式平台下，有些儲存區域是採用只讀儲存器的，如ROM，這樣將“.rodata”段放在該儲存區域中就可以保證程式訪問儲存器的正確性。</p>

<p>另外值得一提的是，有時候編譯器會把字串常量放到“.data”段，而不會單獨放在“.rodata”段。有興趣的讀者可以試著把SimpleSection.c的檔名改成SimpleSection.cpp，然後用各種MSVC編譯器編譯一下看看字串常量的存放情況。</p>

<p>3.3.3 BSS段</p>

<p>.bss段存放的是未初始化的全域性變數和區域性靜態變數，如上述程式碼中<code>global_uninit_var</code>和<code>static_var2</code>就是被存放在.bss段，其實更準確的說法是.bss段為它們預留了空間。但是我們可以看到該段的大小只有4個位元組，這與<code>global_uninit_var</code>和<code>static_var2</code>的大小的8個位元組不符。</p>

<p>其實我們可以透過符號表（Symbol Table）（後面章節介紹符號表）看到，只有<code>static_var2</code>被存放在了.bss段，而<code>global_uninit_var</code>卻沒有被存放在任何段，只是一個未定義的“COMMON符號”。這其實是跟不同的語言與不同的編譯器實現有關，有些編譯器會將全域性的未初始化變數存放在目的檔.bss段，有些則不存放，只是預留一個未定義的全域性變數符號，等到最終連結成執行檔的時候再在.bss段分配空間。我們將在“弱符號與強符號”和“COMMON塊”這兩個章節深入分析這個問題。原則上講，我們可以簡單地把它當作全域性未初始化變數存放在.bss段。值得一提的是編譯單元內部可見的靜態變數（比如給<code>global_uninit_var</code>加上static修飾）的確是存放在.bss段的，這一點很容易理解。</p>

<p>Quiz 變數存放位置</p>

<p>現在讓我們來做一個小的測試，請看以下程式碼：</p>

<pre>static int x1 = 0;
static int x2 = 1;
</pre>

<p>x1和x2會被放在什麼段中呢？</p>

<p>x1會被放在.bss中，x2會被放在.data中。為什麼一個在.bss段, 一個在.data段？ 因為x1為0，可以認為是未初始化的，因為未初始化的都是0，所以被最佳化掉了可以放在.bss，這樣可以節省磁碟空間，因為.bss不佔磁碟空間。另外一個變數x2初始化值為1，是初始化的，所以放在.data段中。</p>

<p>這種類似的編譯器的最佳化會對我們分析系統軟體背後的機制帶來很多障礙，使得很多問題不能一目瞭然，本書將盡量避開這些最佳化過程，還原機制和原理本身。</p>

<p><span><img alt="" src="../images/3-0-2.jpg"/></span> <span>表3-2 …</span></p>

<p>這些段的名字都是由“.”作為字首，表示這些表的名字是系統保留的，應用程式也可以使用一些非系統保留的名字作為段名。比如我們可以在ELF檔案中插入一個“music”的段，裡面存放了一首MP3音樂，當ELF檔案執行起來以後可以讀取這個段播放這首MP3。但是應用程式自定義的段名不能使用“.”作為字首，否則容易跟系統保留段名衝突。一個ELF檔案也可以擁有幾個相同段名的段，比如一個ELF檔案中可能有兩個或兩個以上叫做“.text”的段。還有一些保留的段名是因為ELF檔案歷史遺留問題造成的，以前用過的一些名字如.sdata、.tdesc、.sbss、.lit4、.lit8、.reginfo、.gptab、.liblist、.conflict。可以不用理會這些段，它們已經被遺棄了。</p>

<p>自定義段</p>

<p>正常情況下，GCC編譯出來的目的檔中，程式碼會被放到“.text”段，全域性變數和靜態變數會被放到“.data”和“.bss”段，正如我們前面所分析的。但是有時候你可能希望變數或某些部分程式碼能夠放到你所指定的段中去，以實現某些特定的功能。比如為了滿足某些硬體的記憶體和I/O的地址佈局，或者是像Linux作業系統核心中用來完成一些初始化和使用者空間複製時出現頁錯誤異常等。GCC提供了一個擴充套件機制，使得程式設計師可以指定變數所處的段：</p>

<pre>__attribute__((section("FOO"))) int global = 42;

__attribute__((section("BAR"))) void foo()
{
}
</pre>

<p>我們在全域性變數或函式之前加上“__<code>attribute__((section(“name”)))</code>”屬性就可以把相應的變數或函式放到以“<code>name</code>”作為段名的段中。</p>
