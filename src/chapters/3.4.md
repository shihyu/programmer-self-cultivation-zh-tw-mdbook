<p><span><img alt="" src="../images/3-4.jpg"/></span> <span>圖3-4 ELF 結構 …</span></p>

<p>ELF目的檔格式的最前部是ELF檔案頭（ELF Header），它包含了描述整個檔案的基本屬性，比如ELF檔案版本、目標機器型號、程式入口地址等。緊接著是ELF檔案各個段。其中ELF檔案中與段有關的重要結構就是段表（Section Header Table），該表描述了ELF檔案包含的所有段的資訊，比如每個段的段名、段的長度、在檔案中的偏移、讀寫許可權及段的其他屬性。接著將詳細分析ELF檔案頭、段表等ELF關鍵的結構。另外還會介紹一些ELF中輔助的結構，比如字串表、符號表等，這些結構我們在本節只是簡單介紹一下，到相關章節中再詳細展開。</p>

<p>最開始的4個位元組是所有ELF檔案都必須相同的標識碼，分別為0x7F、0x45、0x4c、0x46，第一個位元組對應ASCII字元裡面的DEL控制符，後面3個位元組剛好是ELF這3個字母的ASCII碼。這4個位元組又被稱為ELF檔案的魔數，幾乎所有的執行檔格式的最開始的幾個位元組都是魔數。比如a.out格式最開始兩個位元組為 0x01、0x07；PE/COFF檔案最開始兩個個位元組為0x4d、0x5a，即ASCII字元MZ。這種魔數用來確認檔案的型別，作業系統在載入執行檔的時候會確認魔數是否正確，如果不正確會拒絕載入。</p>

<p>接下來的一個位元組是用來標識ELF的檔案類的，0x01表示是32位的，0x02表示是64位的；第6個字是位元組序，規定該ELF檔案是大端的還是小端的（見附錄：位元組序）。第7個位元組規定ELF檔案的主版本號，一般是1，因為ELF標準自1.2版以後就再也沒有更新了。後面的9個位元組ELF標準沒有定義，一般填0，有些平台會使用這9個位元組作為擴充套件標誌。</p>

<p>各種魔數的由來</p>

<p>a.out格式的魔數為0x01、0x07，為什麼會規定這個魔數呢？</p>

<p>UNIX早年是在PDP小型機上誕生的，當時的系統在載入一個執行檔後直接從檔案的第一個位元組開始執行，人們一般在檔案的最開始放置一條跳轉（jump）指令，這條指令負責跳過接下來的7個機器字的檔案頭到執行檔的真正入口。而0x01 0x07這兩個位元組剛好是當時PDP-11的機器的跳轉7個機器字的指令。為了跟以前的系統保持相容性，這條跳轉指令被當作魔數一直被保留到了幾十年後的今天。</p>

<p>計算機系統中有很多怪異的設計背後有著很有趣的歷史和傳統，瞭解它們的由來可以讓我們瞭解到很多很有意思的事情。這讓我想起了經濟學裡面所謂的“路徑依賴”，其中一個很有意思的叫“馬屁股決定太空梭”的故事在網上流傳很廣泛，有興趣的話你可以在google以“馬屁股”和“太空梭”作為關鍵字搜尋一下。</p>

<p>ELF檔案標準歷史</p>

<p>20世紀90年代，一些廠商聯合成立了一個委員會，起草並發布了一個ELF檔案格式標準供公開使用，並且希望所有人能夠遵循這項標準並且從中獲益。1993年，委員會發布了ELF檔案標準。當時參與該委員會的有來自於編譯器的廠商，如Watcom和Borland；來自CPU的廠商如IBM和Intel；來自作業系統的廠商如IBM和Microsoft。1995年，委員會發布了ELF 1.2標準，自此委員會完成了自己的使命，不久就解散了。所以ELF檔案格式標準的最新版本為1.2。</p>

<p>檔案型別 <code>e_type</code>成員表示ELF檔案型別，即前面提到過的3種ELF檔案型別，每個檔案型別對應一個常量。系統透過這個常量來判斷ELF的真正檔案型別，而不是透過檔案的副檔名。相關常量以“<code>ET_”</code></p>

<p>3.4.2 段表</p>

<p>我們知道ELF檔案中有很多各種各樣的段，這個段表（Section Header Table）就是儲存這些段的基本屬性的結構。段表是ELF檔案中除了檔案頭以外最重要的結構，它描述了ELF的各個段的資訊，比如每個段的段名、段的長度、在檔案中的偏移、讀寫許可權及段的其他屬性。也就是說，ELF檔案的段結構就是由段表決定的，編譯器、連結器和載入器都是依靠段表來定位和訪問各個段的屬性的。段表在ELF檔案中的位置由ELF檔案頭的“<code>e_shoff</code>”成員決定，比如SimpleSection.o中，段表位於偏移0x118。</p>

<p>前文中我們使用了“objudmp -h”來檢視ELF檔案中包含的段，結果是SimpleSection裡面看到了總共有6個段，分別是<code>“.code</code><code>”、“.data</code><code>”、“.bss</code>”、“.<code>rodata</code>”、“.<code>comment</code>”和“.<code>note.GNU-stack</code>”。實際上的情況卻有所不同，“objdump -h”命令只是把ELF檔案中關鍵的段顯示了出來，而省略了其他的輔助性的段，比如：符號表、字串表、段名字串表、重定位表等。我們可以使用readelf工具來檢視ELF檔案的段，它顯示出來的結果才是真正的段表結構：</p>

<p>3.4.3 重定位表</p>

<p>我們注意到，SimpleSection.o中有一個叫做“.rel.text”的段，它的型別（<code>sh_type</code>）為“<code>SHT_REL</code>”，也就是說它是一個重定位表（Relocation Table）。正如我們最開始所說的，連結器在處理目的檔時，需要對目的檔中某些部位進行重定位，即程式碼段和資料段中那些對絕對地址的引用的位置。這些重定位的資訊都記錄在ELF檔案的重定位表裡面，對於每個需要重定位的程式碼段或資料段，都會有一個相應的重定位表。比如SimpleSection.o中的“.rel.text”就是針對“.text”段的重定位表，因為“.text”段中至少有一個絕對地址的引用，那就是對“printf”函式的呼叫；而“.data”段則沒有對絕對地址的引用，它只包含了幾個常量，所以SimpleSection.o中沒有針對“.data”段的重定位表“.rel.data”。</p>

<p>一個重定位表同時也是ELF的一個段，那麼這個段的型別（<code>sh_type</code>）就是“<code>SHT_REL</code>”型別的，它的“<code>sh_link</code>”表示符號表的下標，它的“<code>sh_info</code>”表示它作用於哪個段。比如“.rel.text”作用於“.text”段，而“.text”段的下標為“1”，那麼“.rel.text”的“<code>sh_info</code>”為“1”。</p>

<p>3.4.4 字串表</p>

<p>ELF檔案中用到了很多字串，比如段名、變數名等。因為字串的長度往往是不定的，所以用固定的結構來表示它比較困難。一種很常見的做法是把字串集中起來存放到一個表，然後使用字串在表中的偏移來引用字串。比如表3-12這個字串表。</p>

<p><span><img alt="" src="../images/3-0-13.jpg"/></span> <span>表3-13 …</span></p>

<p>透過這種方法，在ELF檔案中引用字串只需要給出一個數字下標即可，不用考慮字串長度的問題。一般字串表在ELF檔案中也以段的形式儲存，常見的段名為“.strtab”或“.shstrtab”。這兩個字串表分別為字串表（String Table）和段表字串表（Section Header String Table）。顧名思義，字串表用來儲存普通的字串，比如符號的名字；段表字串表用來儲存段表中用到的字串，最常見的就是段名（<code>sh_name</code>）。</p>

<p>接著我們再回頭看這個ELF檔案頭中的“<code>e_shstrndx</code>”的含義，我們在前面提到過，“<code>e_shstrndx</code>”是<code>Elf32_Ehdr</code>的最後一個成員，它是“Section header string table index”的縮寫。我們知道段表字串表本身也是ELF檔案中的一個普通的段，知道它的名字往往叫做“.shstrtab”。那麼這個“<code>e_shstrndx</code>”就表示“.shstrtab”在段表中的下標，即段表字串表在段表中的下標。前面的SimpleSection.o中，“<code>e_shstrndx</code>”的值為8，我們再對照“<code>readelf -S</code>”的輸出結果，可以看到“.shstrtab”這個段剛好位於段表中的下標為8的位置上。由此，我們可以得出結論，只有分析ELF檔案頭，就可以得到段表和段表字串表的位置，從而解析整個ELF檔案。</p>
