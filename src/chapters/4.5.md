<h2>4.5 靜態函式庫連結</h2>

<p>程式之所以有用，因為它會有輸入輸出，這些輸入輸出的物件可以是資料，可以是人，也可以是另外一個程式，還可以是另外一台計算機，一個沒有輸入輸出的程式沒有任何意義。但是一個程式如何做到輸入輸出呢？最簡單的辦法是使用作業系統提供的應用程式程式設計介面（API, Application Programming Interface）。當然，作業系統也只是一個程式，它怎麼實現跟人機互動裝置、跟其他計算機以及其他程式互動呢？這一點我們在第1章介紹作業系統和I/O時已經簡單介紹過了。</p>

<p>讓我們還是先回到一個比較初步的問題，就是程式如何使用作業系統提供的API。在一般的情況下，一種語言的開發環境往往會附帶有語言庫（Language Library）。這些庫就是對作業系統的API的包裝，比如我們經典的C語言版“Hello World”程式，它使用C語言標準庫的“printf”函式來輸出一個字串，“printf”函式對字串進行一些必要的處理以後，最後會呼叫作業系統提供的API。各個作業系統下，往終端輸出字串的API都不一樣，在Linux下，它是一個“write”的系統呼叫，而在Windows下它是“WriteConsole”系統API。</p>

<p>庫裡面還帶有那些很常用的函式，比如C語言標準庫裡面有很常用一個函式取得一個字串的長度叫<code>strlen()，</code>該函式即遍曆整個字串後返回字串長度，這個函式並沒有呼叫任何作業系統的API，也沒有做任何輸入輸出。但是很大一部分庫函式都是要呼叫作業系統的API的，比如最常用的往終端輸出格式化字串的printf就是會呼叫作業系統，往終端裡面列印一些字串。我們將在第4部分更加詳細地介紹庫的概念。這裡我們只是簡單地介紹靜態函式庫的連結過程。</p>

<p>其實一個靜態函式庫可以簡單地看成一組目的檔的集合，即很多目的檔經過壓縮打包後形成的一個檔案。比如我們在Linux中最常用的C語言靜態函式庫libc位於/usr/lib/libc.a，它屬於glibc專案的一部分；像Windows這樣的平台上，最常使用的C語言庫是由整合開發環境所附帶的執行庫，這些庫一般由編譯器廠商提供，比如Visual C++附帶了多個版本的C/C++執行庫。表4-3列出了VC2008（內部版本號VC9）所附帶的一部分C執行庫（庫檔案存放在VC安裝目錄下的lib\目錄）。</p>

<p>表4-3中只是簡單列舉了幾種C語言執行庫，我們在這裡將介紹一個程式的目的檔如何與C語言執行庫連結形成一個執行檔。關於庫的更詳細內容，將在第4部分展開討論。</p>

<p>我們知道在一個C語言的執行庫中，包含了很多跟系統功能相關的程式碼，比如輸入輸出、檔案操作、時間日期、記憶體管理等。glibc本身是用C語言開發的，它由成百上千個C語言原始碼檔案組成，也就是說，編譯完成以後有相同數量的目的檔，比如輸入輸出有printf.o，scanf.o；檔案操作有fread.o，fwrite.o；時間日期有date.o，time.o；記憶體管理有malloc.o等。把這些零散的目的檔直接提供給庫的使用者，很大程度上會造成檔案傳輸、管理和組織方面的不便，於是通常人們使用“ar”壓縮程式將這些目的檔壓縮到一起，並且對其進行編號和索引，以便於查詢和檢索，就形成了libc.a這個靜態函式庫檔案。在我的機器上，該檔案有2.8 MB大小，我們也可以使用“ar”工具來檢視這個檔案包含了哪些目的檔：</p>

<p>libc.a裡面總共包含了1 400個目的檔，那麼，我們如何在這麼多目的檔中找到“printf”函式所在的目的檔呢？答案是使用“objdump”或“readelf”加上文字查詢工具如“grep”，使用“objdump”檢視libc.a的符號可以發現如下結果：</p>

<pre>$objdump -t libc.a

<p>可以看到“printf”函式被定義在了“printf.o”這個目的檔中。這裡我們似乎找到了最終的機制，那就是“Hello World”程式編譯出來的目的檔只要和libc.a裡面的“printf.o”連結在一起，最後就可以形成一個可用的執行檔了。這個解釋似乎很完美，實際上已經很接近最後的答案了。那麼我們就按照這個方案去嚐試一下，假設“Hello World”程式的原始碼為“hello.c”，使用如下方法編譯：</p>

<pre>$gcc –c –fno-builtin hello.c</pre>

<p>我們得到了目的檔為“hello.o”，為什麼這裡要使用“-<code>fno-builtin</code>”引數是因為預設情況下，GCC會自作聰明地將“Hello World”程式中只使用了一個字串引數的“printf”替換成“puts”函式，以提高執行速度，我們要使用“-<code>fno-builtin</code>”關閉這個內建函式最佳化選項。現在我們還缺“printf.o”，透過“ar”工具解壓出“printf.o”：</p>

<pre>$ar –x libc.a</pre>

<p>這個命令會將libc.a中的所有目的檔“解壓”至當前目錄。我們也可以找到“printf.o”，然後將其與“hello.o”連結在一起：</p>

<pre>$ld hello.o printf.o
ld: warning: cannot find entry symbol _start; defaulting to 0000000008048080
printf.o: In function `_IO_printf':
(.text+0x18): undefined reference to `stdout'
printf.o: In function `_IO_printf':
(.text+0x20): undefined reference to `vfprintf'
</pre>

<p>連結卻失敗了，原因是缺少兩個外部符號的定義。其實眼尖的讀者可能已經在最開始列印“printf.o”的符號表時就看出一點問題來了，那就是“printf.o”裡面有兩個“UND”的符號“stdout”和“vfprintf”，也就是有兩個未定義的符號。正是這兩個未定義的符號打破了看似完美的解釋，很明顯：“printf.o”依賴於其他的目的檔。</p>

<p>用同樣的方法，我們可以找到“stdout”這個符號所在的目的檔，它位於“stdio.o”；而“vfprintf”位於“vfprintf.o”。很不幸的是這兩個檔案還依賴於其他的目的檔，因為它們也有未定義的符號。這些變數和函式都分佈在glibc的各個目的檔之中，如果我們能夠一一將它們收集齊，那麼理論上就可以將它們連結在一起，最後跟“hello.o”連結成一個執行檔。但是，如果靠人工這樣做的代價實在是太大了，我們在這裡不打算演示這樣一個繁瑣的過程。幸好ld連結器會處理這一切繁瑣的事務，自動尋找所有需要的符號及它們所在的目的檔，將這些目的檔從“libc.a”中“解壓”出來，最終將它們連結在一起成為一個執行檔。那麼我們可不可以就這麼認為：將“hello.o”和“libc.a”連結起來就可以得到執行檔呢？理論上這樣就可以了，如圖4-6所示。</p>

<p>Q&amp;A</p>

<p>Q：為什麼靜態執行庫裡面一個目的檔只包含一個函式？比如libc.a裡面printf.o只有printf()函式、strlen.o只有strlen()函式，為什麼要這樣組織？</p>

<p>A：我們知道，連結器在連結靜態函式庫的時候是以目的檔為單位的。比如我們引用了靜態函式庫中的printf()函式，那麼連結器就會把庫中包含printf()函式的那個目的檔連結進來，如果很多函式都放在一個目的檔中，很可能很多沒用的函式都被一起連結進了輸出結果中。由於執行庫有成百上千個函式，數量非常龐大，每個函式獨立地放在一個目的檔中可以盡量減少空間的浪費，那些沒有被用到的目的檔（函式）就不要連結到最終的輸出檔案中。</p>
