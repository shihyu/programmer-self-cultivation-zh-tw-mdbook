<h2>8.2 符號版本</h2>

<p>歷史回顧</p>

<p>在一些早期的系統中，應用程式在被構建時，靜態連結器會把程式所依賴的所有共用函式庫的名字、主版本號和次版本號都記錄到最終的應用程式二進位輸出檔案中。在執行時，由於動態連結器知道應用程式所依賴的共用函式庫的確切版本號，所以相容性問題比較容易處理。比如在SunOS 4.x中，動態連結器會根據程式的共用函式庫依賴列表中的記錄，在系統中查詢相同共用函式庫名和主版本號的共用函式庫；如果某個共用函式庫在系統中存在相同主版本號不同次版本號的多個副本，那麼動態連結器會使用那個最高次版本號的副本。</p>

<p>動態連結器在查詢共用函式庫過程中，如果找到的共用函式庫的次版本號高於或等於依賴列表中的版本，那麼連結器就預設共用函式庫滿足要求，因為更高次版本號的共用函式庫肯定包含所有需要的符號；如果找到的共用函式庫次版本號低於所需要的版本，SunOS 4.x系統的策略是向使用者發出一個警告資訊，表示系統中僅有低次版本號的共用函式庫，但執行程式還是繼續執行。程式很有可能能夠正常執行，比如該程式只用了低次版本號中的介面，而沒有用到高次版本號中新新增的那些介面。當然，程式如果用到了高次版本號中新新增的介面而目前系統中的低次版本號的共用函式庫中不存在，那麼就會發生重定位錯誤。有些採取更加保守策略的系統中，對於這種系統中沒有足夠高的次版本號滿足依賴關係的情況，程式將會被禁止執行，以防止出現意外情況。</p>

<p>這兩種策略或可能導致程式執行錯誤（第一種只透過警告的策略），或者會阻止那些實際上能夠執行的程式（第二種保守策略）。實際上很多應用程式在高次版本的系統中都有構建，但實際上它只用到了低次版本的那部分介面，在採取第二種策略的系統中，如果系統中只有低次版本號的共用函式庫，那麼這些程式就不能執行。我們可以把這個問題叫做次版本號交會問題（Minor-revision Rendezvous Problem）。</p>

<p>次版本號交會問題並沒有因為SO-NAME而解決</p>

<p>動態連結器在進行動態連結時，只進行主版本號的判斷，即只判斷SO-NAME，如果某個被依賴的共用函式庫SO-NAME與系統中存在的實際共用函式庫SO-NAME一致，那麼系統就認為介面相容，而不再進行相容性檢查。這樣就會出現一個問題，當某個程式依賴於較高的次版本號的共用函式庫，而執行於較低次版本號的共用函式庫系統時，就可能產生缺少某些符號的錯誤。因為次版本號只保證向後相容，並不保證向前相容，新版的次版本號的共用函式庫可能新增了一些舊版沒有的符號。這種次版本號交會問題並沒有因為SO-NAME的存在而得到任何改善。對於這個問題，現代的系統透過一種更加精巧的方式來解決，那就是符號版本機制。</p>

<p>正常情況下，為了表示某個共用函式庫中增加了一些介面，我們就把這個共用函式庫的次版本號升高（表示裡面新增了一些東西）。但是我們需要一種更為巧妙的方法，來解決次版本號交會問題。Linux下的Glibc從版本2.1之後開始支援一種叫做基於符合的版本機制（Symbol Versioning）的方案。這個方案的基本思路是讓每個匯出和匯入的符號都有一個相關聯的版本號，它的實際做法類似於名稱修飾的方法。與以往簡單地將某個共用函式庫的版本號重新命名不同（比如將libfoo.so.1.2升級到libfoo.so.1.3），當我們將libfoo.so.1.2升級至1.3時，仍然保持libfoo.so.1這個SO-NAME，但是給在1.3這個新版中新增的那些全域性符號打上一個標記，比如“VERS_1.3”。那麼，如果一個共用函式庫每一次次版本號升級，我們都能給那些在新的次版本號中新增的全域性符號打上相應的標記，就可以清楚地看到共用函式庫中的每個符號都擁有相應的標簽，比如“VERS_1.1”、“VERS_1.2”、“VERS_1.3”、“VERS_1.4”。</p>

<p>8.2.2 Solaris中的符號版本機制</p>

<p>這個基於符號版本的方案最早是Sun在1995年的Solaris 2.5中實現的，在這個新的機制中，Solaris的ld連結器為共用函式庫新增了版本機制（Versioning）和範圍機制（Scoping）。</p>

<p>版本機制的想法很簡單，也就是定義一些符號的集合，這些集合本身都有名字，比如叫“VERS_1.1”、“VERS_1.2”等，每個集合都包含一些指定的符號，除了可以擁有符號以外，一個集合還可以包含另外一個集合，比如“VERS_1.2”可以包含集合“VERS_1.1”。就概念而言與其說是“包含”，不如說是“繼承”，比如“VERS_1.2”的符號集合包含（繼承）了所有“VERS_1.1”的符號，並且包含所有“VERS_1.2”的符號。</p>

<p>那麼，這些集合的定義及它們包含哪些符號是怎樣指定的呢？在Solaris中，程式設計師可以在連結共用函式庫時編寫一種叫做符號版本指令碼的檔案，在這個檔案中指定這些符號與集合之間及集合與集合之間的繼承依賴關係。連結器在連結時根據符號版本指令碼中指定的關係來產生共用函式庫，並且設定符號的集合與它們之間的關係。</p>

<p>舉個簡單的例子，假設有個名為libstack.so.1的共用函式庫編寫的符號版本指令碼檔案如下：</p>

<pre>SUNW_1.1 { 
    global: 
    pop; 
    push; 
} 
  
SUNWprivate { 
    global: 
    __pop; 
    __push; 
    local: 
    *; 
} 
</pre>

<p>在這個指令碼檔案中，我們可以看到它定義了兩個符號集合，分別為“<code>SUNW_1.1</code>”和“<code>SUNWprivate</code>”（在Solaris系統中，符號的集合名通常由“<code>SUNW</code>”開頭）。第一個包含了兩個全域性符號<code>pop</code>和<code>push</code>；在第二個集合中，包含了兩個全域性符號<code>“__pop</code>”和<code>“__push</code>”。第二個集合中最後的“<code>local:</code> *;”表示：除了上述被標識為全域性的“<code>pop</code>”、“<code>push</code>”、“__<code>pop</code>”和<code>“__push</code>”這4個符號以外，共用函式庫中其他的本來是全域性的符號都將成為共用函式庫區域性符號，也就是說連結器會把原先是全域性的符號全部變成區域性的，這樣一來，共用函式庫外部的應用程式或其他的共用函式庫將無法訪問這些符號。這種方式可以用於保護那些共用函式庫內部的公用實用函式，但是共用函式庫的作者又不希望共用函式庫的使用者能夠有意或無意地訪問這些函式。這種方法又被稱為範圍機制（Scoping），它實際上是對C語言沒有很好的符號可見範圍的控制機制的一種補充，或者說是一種補救性質的措施。</p>

<p>假設現在這個共用函式庫升級了，在原有的基礎上新增了一個全域性函式“swap”，那麼新的符號版本指令碼檔案可以在原有的基礎上新增如下內容：</p>

<pre>SUNW_1.2 { 
    global: 
    swap; 
} SUNW_1.1; 
</pre>

<p>上面的指令碼就表示了一個典型的向上相容的介面：1.2版的共用函式庫增加了一個swap介面，並且它繼承了1.1的所有介面。那麼我們可以按照這種方式，共用函式庫中的版本序號SUNW_1.1、SUNW_1.2、SUNW_1.3……分別表示每次共用函式庫新增介面以後的更新，它們依次向後繼承，向後相容。這裡值得一提的是，跟在“SUNW_”字首後面的版本號由主版本號與一個次版本號構成，這裡的主版本號對應於共用函式庫實際的SO-NAME中的主版本號。</p>

<p>當共用函式庫的符號都有了版本集合之後，一個最明顯的效果就是，當我們在構建（編譯和連結）應用程式的時候，連結器可以在程式的最終輸出檔案中記錄下它所用到的版本符號集合。值得注意的是，程式裡面記錄的不是構建時共用函式庫中版本最新的符號集合，而是程式所依賴的集合中版本號最小的那個（或者那些）。比如，一個共用函式庫libfoo.so.1中有6個符號版本，從SUNW_1.1到SUNW_1.6，某個應用程式app_foo在編譯時，系統中的libfoo.so.1的符號版本為SUNW_1.6，但實際上app_foo只用到了最高到SUNW_1.3集合的符號，那麼應用程式實際上依賴於SUNW_1.3，而不是SUNW_1.6。連結器會計算出app_foo所用到的最高版本的符號，然後把SUNW_1.3記錄到app_foo的執行檔內。</p>

<p>在程式執行時，動態連結器會透過程式內記錄的它所依賴的所有共用函式庫的符號集合版本資訊，然後判定當前系統共用函式庫中的符號集合版本是否滿足這些被依賴的符號集合。透過這樣的機制，就可以保證那些在高次版本共用函式庫的系統中編譯的程式在低次版本共用函式庫中執行。如果該低次版本的共用函式庫滿足符號集合的要求，比如app_foo在libfoo.so.1次版本號大於等於3的系統中執行，就沒有任何問題；如果低次版本共用函式庫不滿足要求，如app_foo在libfoo.so.1次版本號小於3的系統中執行，動態連結器就會意識到當前系統的共用函式庫次版本號不滿足要求，從而阻止程式執行，以防止造成進一步的損失。</p>

<p>這種符號版本的方法是對SO-NAME機制保證共用函式庫主版本號一致的一種非常好的補充。</p>

<p>8.2.3 Linux中的符號版本</p>

<p>Linux系統下共用函式庫的符號版本機制並沒有被廣泛應用，主要使用共用函式庫符號版本機制的是Glibc軟體包中所提供的20多個共用函式庫。這些共用函式庫比較有效地利用了符號版本機制來表示符號的版本演化及利用範圍機制來遮蔽一些不希望暴露給共用函式庫使用者的符號。對於目前2.6.1的Glibc中的C語言執行庫libc-2.6.1.so來說，它的符號版本演化如下：</p>

<p>GLIBC_2.0、GLIBC_2.1、GLIBC_2.1.1、GLIBC_2.1.2、GLIBC_2.1.3、GLIBC_2.2、GLIBC_2.2.1、GLIBC_2.2.2、GLIBC_2.2.3、GLIBC_2.2.4、GLIBC_2.2.6、GLIBC_2.3、GLIBC_2.3.2、GLIBC_2.3.3、GLIBC_2.3.4、GLIBC_2.4、GLIBC_2.5、GLIBC_2.6</p>

<p>對於有些像Glibc中的加密解密庫libcrypt，它目前的共用函式庫版本是libcrypt-2.6.1.so，但是它內部的符號版本只有GLIBC_2.0，因為它的介面十分穩定，從2.0版本之後就沒有改動過。另外我們在Glibc的庫中還可以看到類似於“GCC_”為字首及“GLIBC_PRIVATE”這樣的符號版本，這樣的符號版本標記分別用於GCC編譯器和GLIBC內部，它提醒共用函式庫的使用者：最好不要使用這些符號，因為它並不是對外公開的，有可能隨著共用函式庫的版本演化而被刪除或改變，總之一句話，後果自負。</p>

<p>GCC對Solaris符號版本機制的擴充套件</p>

<p>GCC在Solaris系統中的符號版本機制的基礎上還提供了兩個擴充套件。第一個擴充套件是，除了可以在符號版本指令碼中指定符號的版本之外，GCC還允許使用一個叫做“.symver”的組譯宏指令來指定符號的版本，這個組譯宏指令可以被用在GAS組譯中，也可以在GCC的C/C++原始碼中以嵌入組語指令的模式使用。它的用法如下：</p>

<pre>asm(".symver add, add@VERS_1.1");

int add(int a, int b)
{
    return a + b;
}
</pre>

<p>這樣就可以把符號“add”指定為符號標簽“VERS_1.1”。第二個擴充套件是GCC允許多個版本的同一個符號存在於一個共用函式庫中，也就是說，在連結層面提供了某種形式的符號過載機制，比如：</p>

<pre>asm(".symver old_printf, printf@VERS_1.1");
asm(".symver new_printf, printf@VERS_1.2");

int old_printf()
{
    ...
}

int new_printf()
{
    ...
}
</pre>

<p>為什麼要提供這種符號多版本過載機制呢？有時候當我們對共用函式庫進行升級的時候，可能僅僅更改了一個符號的介面或含義，那麼，如果僅僅為了這個符號的更改而升級主版本號，那麼將會對系統帶來很大的影響。理想的情況是，當共用函式庫發生比較小的變化時，新版的共用函式庫能夠在原來的基礎上做些補充，而並不影響舊版的功能，即能完全保持向後相容性，爭取做到不更改共用函式庫的SO-NAME，即不更改主版本號。</p>

<p>Solaris 2.5系統的符號版本方案有一個不足，那就是同一個共用函式庫中，每個函式只能有一個版本號，也就是說不允許多個版本的同一個函式名存在，只允許該函式的某個版本存在。比如符號foo要麼是VERS_1.0，要麼是VERS_1.1，不允許這兩個版本同時存在。Linux下的符號版本機制比Salaris 2.5的要先進一些，它允許同一個名稱的符號存在多個版本。當某個符號在新的共用函式庫版本中介面被更改或符號的含義被改變，那麼共用函式庫可以保留原來的版本符號，比如前面例子中匯出的printf 1.1版實際上即為old_printf；而將新版的new_printf匯出成printf版本1.2。這樣，連結器可以挑選符合某個程式版本號的符號來進行連結，使用1.1版printf的程式會被連結到old_printf，而使用1.2版的程式會被連結到new_printf，所有的程式都可以正確執行，更改函式的介面和含義並不影響舊版程式的執行。</p>

<p>Linux系統中符號版本機制實踐</p>

<p>在Linux下，當我們使用ld連結一個共用函式庫時，可以使用“--<code>version-script</code>”引數；如果使用GCC，則可以使用“-<code>Xlinker</code>”引數加“--<code>version-script</code>”，相當於把“--<code>version-script</code>”傳遞給ld連結器。如編譯原始碼為“lib.c”，符號版本指令碼檔案為“lib.ver”：</p>

<pre>gcc -shared -fPIC lib.c -Xlinker --version-script lib.ver -o lib.so</pre>

<p>假設lib.c裡面定義了一個foo的函式，而main.c呼叫了這個函式，如我們使用下面的符號版本指令碼編譯一個lib.so：</p>

<pre>VERS_1.2 {
    global:
        foo;
    local:
        *;
};
</pre>

<p>那麼很明顯，這個版本的lib.so裡面foo的符號版本是VERS_1.2。然後將main.c編譯並且連結到當前版本的lib.so：</p>

<pre>gcc main.c ./lib.so –o main</pre>

<p>於是main程式裡面所引用的foo也是VERS_1.2的。如果把這個main程式拿到一台只包含低於VERS_1.2的foo的lib.so系統中執行，那麼動態連結器就會報執行錯誤並且退出程式，防止了符號版本不符所造成額外的損失：</p>

<pre>./main
./main: ./lib.so: version `VERS_1.2' not found (required by ./main)
</pre>
